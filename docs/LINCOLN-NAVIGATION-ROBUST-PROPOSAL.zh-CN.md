# 林肯仪表导航：重新审视后的修复方案

状态：帧级诊断与数值回放已实施，并针对回放中可证明的一种过期终点做了窄范围修复：收到明确不同的新动作编号而尚无对应详情时，不继续重发旧终点。正常路口、真实终点动作、空列表和重规划仍按 `v1.2.0` 逻辑处理。此前“新索引后等待距离”和“终点动作等状态 2”的保护会造成正常导航缺失，已撤回。用户照片发生时的手机原始帧未提供，不能确认该修复就是此次实车现象的原因。

该规则有明确取舍：新动作详情缺失期间，仪表会清除旧终点并等待新详情；如手机永久不发详情，无法保证何时恢复。普通路口保持原有防闪烁逻辑，不因缺详情一律清屏。状态 2、空列表、重规划等待期间保持原有处理。广播 OFF 结果不确定时，后续有效指引会先重发 ON 再发送新指引；仍不能证明第三方仪表实际收到或正确绘制。

## 已核实的链路与边界

1. `BydHudRouteState` 接收手机的 `0x5201` 增量更新：`0x0a` 为下一动作距离，`0x0d` 当前动作列表，现代码只选择第一个；`0x5202` 按索引缓存动作类型及其后道路名。当前保留 `v1.2.0` 的距离缓存行为，新动作详情到达时即使未收到新距离，也继续使用已有距离；这避免了先前测试版可能无限等待，但不能证明缓存距离必然属于新动作。
2. 有开源项目的设备记录把双索引解释成“当前、下一项”，另一项目对其车机采集解释首项为下一动作索引。两者所处设备/固件不同，不能证明本车高德的含义；不能直接固定选第二项。参考：[CPC200 协议字段研究](https://github.com/lvalen91/CPC200-CCPA_resources/blob/main/documentation/02_Protocol_Reference/iap2_message_catalog.md)、[Mazda 选择逻辑](https://github.com/KidMixer/mazda-carplay-hud/blob/main/mazda/patches/blmjcicarplay/nav.cpp)。
3. `0x5202 / 0x05` 在另一开源项目的研究中被描述为相邻动作之间的距离，当前解析器没有使用。它可能对检查索引与路线结构有帮助，但不能未经验证直接当作从车到路口的距离，也不能证明分帧的距离归属。
4. 所提供 InstrumentPanel 1.0 的运行时 DEX 中，`INFO` 解析箭头、距离、路名及身份标识，然后调用同一 `sendNaviInfo`；缺少距离按 0 处理。用空值或 0 模拟“只显示箭头”会产生真实的 0 米和进度副作用，尚未发现可证明安全的该种方式。
5. `turn_dest` 可在路线仍活动、距离非零时发出；运行时转换器把它映射为终点路段代码，但没有车机固件显示文字的证据。当前保留终点动作直接发送的行为，以免地图不发送状态 2 时丢失终点提示。这也意味着只要手机直接提供终点动作，且没有足够证据区分真假，就仍可能误报。另一个开源逆向项目将状态 2 标为 Arrived；另一项目对其捕获中的状态含义表示不确定，因此不假设各种设备均相同。
6. 接收器按 `本次距离 / 该路口首个距离 × 256` 计算进度。把旧路口距离用于新身份会产生错误基准；任意更换身份又会让进度重刷。不能只追求不空白而任意复用距离或重建身份。
7. 当前新增诊断记录合并后的快照，保留最近索引、距离修订等，但无法保证还原索引和距离是否在同一帧：这些值可能分别来自不同帧，且事件会限流。现有用户音频日志未找到可用的路口帧序列。
8. `LincolnClusterProtocol.turnCode` 对未识别的非空动作类型当前回退为直行，与旧方案中“未知不伪造直行”的表述不符。它是既有行为，应作为单独兼容风险分析；不能在没有验证的情况下顺便改变已在用的映射。

## 建议分批

### 1. 明确证据并让诊断可以定位消息顺序

- 保持现有用户已验证的连接、普通转弯、歌词、距离精度、进度滤波和其他车型输出。先不固定把列表第二项当成新动作，不默认 `0x5202` 相邻动作距离就是当前位置距离。
- 为林肯输出保留有界的原始**字段元数据**：每条 `0x5201` 的单调时间、路线状态是否存在、索引列表是否存在/长度/前若干个、距离是否存在及数值/修订、总剩余距离是否存在，以及消息顺序；每条 `0x5202` 只记索引、动作类型和所需字段是否存在。可补充 `0x5201 / 0x02` 动作状态及 `0x5202 / 0x05` 是否存在，含义先不用于控制。不可记录原始载荷、路名、地址、歌词、设备标识、经纬度。
- 缓存容量与事件次数有界；状态/索引变化、缺失和发送结果优先，普通距离节流，并标记漏记。同步内存入队，导出时读取，不在导航回调执行文件或网络 I/O。验证分帧与同帧可区分、隐私、溢出、线程安全和性能。
- 查可公开取得并允许使用的标注帧或已有样本进行离线重放；找不到时保留合成测试并注明无法替代用户地图。不得把其他地图/车机样本当成高德已验证。

### 2. 路口选择与距离关联：先把不确定性作为状态

- 明确每次更新的字段来源、所属本地会话/路线代次及新旧索引，构造仅在林肯输出使用的事件模型，不修改其他车型共享解析的原语义。
- 距离和当前索引在同一消息时，按现有协议证据作为候选；索引明确后到来的新距离按该索引处理。处理前先确认所属路线未结束且重规划已恢复；多索引语义与同帧绑定仍需独立验证。
- 距离先到、索引后到时，在本地保存近期候选及其旧索引、距离、原始顺序与时间；不得仅因相邻几十/几百毫秒就声明属于新索引。结合地图提供的可靠结构字段和重放样本判断是否存在可证明的绑定；比较距离变化、路线总距离、相邻动作间距只能提供辅助证据，不能单独证明或作为默认的强行推断。
- 对未明确归属的情况，设计短时合并与可恢复流程：同一路口短暂缺帧保留旧卡和身份；明确换路口但缺失新距离时不能持续展示旧路口或发送虚构距离，等待后续数据并记录原因。超时不能凭时间凭空证明距离归属；没有可信数据时仍存在仪表短暂或持续缺失的可能。若想在此情形下持续显示，需要先验证接收器支持的安全中性表示或得到手机协议证据。不得承诺完全无缺失。
- 进度身份只在动作和有效距离足以建立新基准后改变；真实旧距离不能冒充新基准。保留前序的抖动、真实回升、短暂无路线、重规划和重发保护。处理 0 时区分真实 0 与缺失，且不能仅凭 0 确认到达。

### 3. 终点动作、真实到达和取消分开验证

- 使用状态、当前动作类型、完整列表、是否存在明确的后续普通动作、真实距离字段及其新鲜度交叉检查。它们含糊或矛盾时，不能把距离阈值、未知索引或旧剩余距离单独当作到达证明；同一消息的字段也必须按该协议的版本与实际语义解释。
- 验证可供仪表表示“即将到达”的中性编码，且只在反编译与可执行接收器模型和目标固件行为都有依据时使用。未验证前，不把未知代码、空类型、0 米冒充中性提示。
- 维持现有终点动作和状态 2 的行为：终点动作无需等待状态 2；状态 2 清理导航，不额外合成终点。状态 0、断连不生成到达。若进一步区别“即将到达”和“已经到达”，必须先通过真实帧或可证实的协议契约验证，不能把短延迟或单一距离阈值当成确认。
- 若没有绝对可信依据，则“肯定不误报”和“所有地图都不丢终点提示”无法同时保证。将其作为未解决的发布阻塞项，保留可观测性，明确实际行为和可用性取舍，而不是给功能完成结论。

## 本地验证与交付条件

- 不要求用户先开车。优先补充现有 0x5201/0x5202 的帧序列回放、属性测试和已提供 InstrumentPanel 1.0 的可执行/反汇编接收器模型。覆盖同帧、距离先/索引先、单帧后再无距离、空列表、两项及以上列表、普通转弯/掉头/环岛、相邻路口、候选冲突、距离 0、目标动作、状态 2/0 缺失和乱序、重规划、重复、断连和快速新路线、兼容开关开关、发送失败与迟到回调。每项都比较基础广播与辅助输出，以及接收器计算出的进度。
- 以已验证版本的普通场景为对照，量化新路口首显是否比旧版延迟、缺失或使用错误值；对无法区分的输入明确标注，不用合成数据宣称真实高德已覆盖。维护原有进度抖动/NoRouteSet 测试，不为非 UI 修改做截图矩阵。
- 验证真实接收器的 `turn_dest` 映射与 `STATE_ON/INFO/STATE_OFF` 的接收行为，但不声称模拟器模拟了用户的真实仪表固件和 iPhone。完成后仅交付测试包；正常使用时如仍有异常再按需提供诊断。无手机源数据和目标固件显示结果时，不能承诺所有场景均已解决或完全没有回退。
