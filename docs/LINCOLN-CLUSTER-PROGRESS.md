# 林肯仪表路口进度接口复核

2026-10-25，对用户提供的 `InstrumentPanel_Optional 1.0` 的运行时 DEX 及 DiPlay `lincoln-0.2.20` 进行复核。

## 可复核依据

- APK SHA-256：`ce1d4742b9b62c747e7b848954eda4f94aaca9d21fb292fb1cd361dcdfa39ef5`。
- 提取的运行时 DEX SHA-256：`4a322cde82fa501e066c5f20418b0d5833c59dade6e8d92b9d14c7b73b3b390e`。
- 广播适配器的导航处理方法：DEX code item `0x23aea0`；字符串解码函数 `0x229b28` 使用循环 XOR。这里解出的输入是 `nextRoadName`、`laneCount`、`name`、`distance`、`latitude`、`longitude`，没有读取 `BargraphSteps`。
- 适配器读取 `distance` 为 int，`latitude` / `longitude` 为 double，缺省值均为零；在 `0x23b034` 调用 `NavPresenterImpl.sendNaviInfo`。
- `NavPresenterImpl.sendNaviInfo`：code item `0x223850`。缓存坐标或传入坐标不同时，记录当前距离为本路口起始距离。基准为零时输出 1，否则按浮点运算计算 `当前距离 / 起始距离 * 256` 后转为 int。
- 计算结果以字符串写入下游 Bundle 的 `BargraphSteps`；`VendorInsClusterController$27` 通过 `CarVendorInstrumentClusterManager.sendEvent(0x21100c29, bundle)` 发送。该 Bundle 不包含路口经纬度。
- 原车 HUD 回调通过 `BNRGManeuver` 的距离及路口经纬度调用同一个 presenter。这说明不能将下游 Bundle 字段直接当作广播输入。

经纬度字段不能省略。省略后接收端取 `(0,0)`，与新实例的初值相同，无法建立非零起始距离，进度停在 1。当前修正仍发送这两个 double 字段，只是使用路口标识替代真实位置。

## DiPlay 修正

删除广播中的 `BargraphSteps`、DiPlay 的 0–256 计算及进度值缓存。保留路口状态跟踪，以便控制接收端何时重新记录距离基准。

当前 iAP2 导航数据模型有路口编号、转向和道路名，没有可直接使用的路口坐标。针对已核实的默认仪表包，使用非零、有限的双精度标识填入 `latitude` / `longitude`，仅适配其“坐标相等表示同一路口”的契约。这些值是合成标识，不是实际位置，不使用车辆实时 GPS，也不宣称取得了真实路口坐标。自定义其他接收包不发送这些标识。

- 有有效 iAP2 路口编号时，以编号识别路口；道路名补全、文字变化和同编号的指令细化仍更新显示字段，但不再重置进度。当前解析器输出的有效导航均有编号；缺编号的旧调用才用指令和路名作启发式回退。
- 同一路口发送距离不变或减小时保持标识。普通重复广播、短暂空帧保持最近显示数据，下一路口编号变化时立即换标识。
- 每次实际发送距离增加都换标识，包括 200→205 米的小幅修正，以及 1,499→1,500 米对应的 1,400→1,500 米显示精度变化。删除“只比较本地起始距离或 50 米阈值”的旧判断。
- 这样，同一标识下发送的距离保持不增：即使漏收前几包，或仪表独立重启，从任意包开始按顺序接收，后续距离也不会超过它实际记录的起始距离，计算保持在 0～256（零基准沿用原 APK 的默认值 1）。不改变已有的距离精度和负数、超范围保护。
- 这一保护有明确取舍：向上修正距离会重新起算进度；不把真实距离压小来掩盖变化。仪表没有基准回执，无法恢复它在重启前丢失的起始距离；重启或漏收后从它首次收到的距离重新起算。
- 明确的导航结束立即使下一条有效导航使用新标识，同时保留最近显示数据经过原有 2.5 秒防闪烁窗口。即使窗口内重开导航并复用路口编号，也不再沿用旧路线基准；结束帧夹带的旧导航字段不会覆盖保留的数据。普通空帧不执行这一重置。
- 接入此前未用于进度的 iAP2 路线状态：`0x5201 / 0x01` 的 Loading（3）和 Rerouting（5）。即使没有结束事件、编号不变、距离缩短，也会启动一次新的本地进度代次；这不是手机提供的路线 ID。连续的加载/重规划帧只启动一次，普通空列表、路名补全、Locating（4）、未知状态均不据此猜测新路线。
- 重规划期间默认仪表继续收到最近成功的导航数据及原标识。恢复 RouteSet（1）或 ProceedToRoute（6）后，必须再收到有效当前列表下的新距离，才用新代次建立基准；状态和距离允许分帧到达，同一帧带齐也可立即恢复。不会把状态恢复帧、歌曲更新或路口文字更新触发的旧距离当作新基准。未变化的编号和路口描述继续使用 iAP2 的增量缓存，不强制手机重发。
- 上述代次和等待标记经 `CarPlayGlance` 传递，单独变化也会通知仪表，不会被“可见字段相同”的去重吞掉。BYD 的原有当前指令/超时策略不变；等待新基准的门控仅用于已核对的默认仪表包，自定义接收包保持原有导航流程。
- 断开和重新启用后使用新标识；应用重启后也不依赖固定从 1 开始的编号，避免与仍运行的仪表缓存相同。
- 导航数据发送异常后，下一有效帧重建标识；保活若重发较早成功的距离，也先换标识，兼容“接收端可能已处理、发送端却收到异常”的结果不确定情况。只有清除状态失败时，仍可继续保留最近数据及其标识。

## 对抗性复现与修正

### RC2 实车反馈后的快照时序修正

用户确认实车进度条已经显示，但路口距离持续减小时仍可能反复重新起算。照片不能确定每次重置的输入原因；源码排查发现并复现了一个会产生同类现象的并发缺陷：`CarPlayGlance` 在状态锁外通知监听者，导航、歌词通知和仪表定时读取可能交错。旧快照晚于新快照进入仪表输出时，发送锁只能保证不同时发送，不能保证数据的新旧顺序。

在 API 25、27、28、33 的确定性测试中，真实 TLV 输入距离 `400 → 125 → 90 → 80`，RC2 实际广播变成 `400 → 125 → 90 → 125 → 80`。多出的旧 `125` 会命中距离回升保护，换路口标识并把进度刷回 256；这不是手机真的报告了距离回升。

修正后，监听回调、首次挂接和定时保活统一在仪表发送锁内读取源状态最新发布的快照，用它替代回调携带的旧对象。读取本身不触发监听通知或超时刷新，避免递归及锁重入导致的额外通知。即使最新通知尚被另一个监听者延迟，也能使用已发布的数据继续发送及保活。真正的结束和断开同时把路线代次留在源状态中，因此即使结束回调晚到而被较新状态替代，后续复用编号的新路线仍会建立一次新基准，也不会在旧结束回调补到时再重置一次。

修正后的同一输入广播为 `400 → 125 → 90 → 80`，独立仪表接收模型输出 `256 → 80 → 57 → 51`，标识始终相同。另覆盖定时读取后被新导航超越、明确结束后马上重新导航、断开重连复用编号等场景。距离精度、真实回升保护、明确重规划、负数保护及仪表接收公式不变，没有压低真实距离来掩盖跳动。

诊断日志补充 `index`、`nav progress baseline reason`（重新起算原因、代次及前后距离），以及 `coalesced superseded glance` 和 `supersededSnapshots` 计数。此复现证明旧代码存在导致重刷的发送端缺陷；尚无这次行车日志，不能断言它解释了实车上的全部重刷。仪表进程重启、手机实际换编号或报告重规划仍可能重新起算。

再次对抗性审查发现，第一轮的“过时回调直接返回”会使部分保活空跑：最新 100 米已经发布、通知被较慢的监听者拖住时，拿着旧 400 米快照的定时任务也被丢弃，仪表仍停在 400 米。这一遗漏在四个 SDK 的测试中复现后，改为上述“发送锁内读取最新已发布值”。补充覆盖旧任务仍可保活、最新终止通知被阻塞时仍正常清除、发送锁竞争期间进入下一路口不被撤回，以及歌词和剩余里程不回退。状态源在释放自身锁后通知监听者；发送锁内只读取已经发布的值，不反向触发通知。

本次修正及再次对抗性补充的完整非视觉回归于 2026-10-25 通过，用时 4 分 6 秒：shared 1,795 项（1 项既有跳过）、common 1,899 项、home 6 项，合计 3,700 项，失败和错误均为零；三个应用的 lint 和 debug 构建全部通过。新增并发场景共 24 项 SDK 检查，仪表广播测试共 132 项。按用户要求未执行视觉截图回归；该修正纳入正式版 1.1.8，已发布的 RC2 不包含此修正。

## 重规划状态依据

2026-10-25 核对两个公开实现的字段含义：

- [mib2q-carplay-rgi 的枚举定义](https://github.com/luka-dev/mib2q-carplay-rgi/blob/a63d54741839c7d30d32dd4e149f693856bcb0db/hook/routeguidance/rgd_tlv.h#L84-L97)，注明来自 MHI3 `CDIONavigationMetadataTypeInfo::toString(ERouteGuidanceState)`；定义 3=Loading、5=Rerouting。
- [OCBM 的 RouteGuidanceState 实现](https://github.com/lvalen91/ocbm/blob/c9a718d0ca49d2f4dff458febc8eb833283a75bd/crates/vendor/metadata/src/types.rs#L41-L72) 使用相同映射，说明分别是获取路线和重新计算路线。仓库原有 `FceNavigationState` 的活动状态定义亦与此一致。

以上用于交叉核对协议解释，并非声称获得 Apple 私有规范或已采集用户手机的重规划流量。新增测试以真实 TLV 格式通过解析器、快照通知和广播，再由 APK 接收公式模型验证；不以直接构造快照代替整条链路。

## 验证边界

`LincolnClusterOutputTest` 中的独立接收模型来自上述 APK 的字段读取及计算逻辑，保留默认值 1、浮点计算和不钳制的原始行为。测试包括旧广播失效、正常进度、上述复现，以及从任意首包开始接收、不同间隔丢包、取整边界、零距离恢复、异常距离和生命周期回归。测试逐包检查实际广播的字段与类型；不假设发送成功等于接收成功。

RC2 发布前的重规划变更已执行仓库规定的单元测试、三个应用的 lint 及 debug 构建，全部通过（2026-10-25，3 分 36 秒）。shared 1,771 项（1 项既有跳过）、common 1,899 项、home 6 项，失败和错误均为零；其中仪表广播测试在 API 25/27/28/33 共 108 项。公开源码凭据检查及 4 项更新镜像脚本测试也通过。该轮按用户要求跳过视觉截图回归，没有安装模拟器。

该验证确认发送端与这份 APK 的代码契约一致，不等于在真实硬件或所有同包名固件上完成显示验证，也不证明系统实际交付了广播。丢包保护的范围是同一发送端的有序广播子序列；此接口没有接收回执、序号或恢复原始基准的字段。若更换仪表 APK，需重新确认坐标字段仍然只作为身份标识使用。

若手机既不发结束事件，也不发 Loading/Rerouting，仍复用编号且距离不增加，现有信息依然无法区分新路线与正常前进；不能用定时或路名变化保证识别。若报告重规划后始终不报告恢复状态及新距离，则保持旧数据显示，直至新有效数据、明确结束或断开，不伪造新的进度基准。诊断日志新增进度代次及等待状态，便于区分“重规划信号未发送”和“已收到但等待完整恢复数据”。
