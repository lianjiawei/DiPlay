# 日志写入性能修复与回归边界

本轮承接 `PERFORMANCE-REVIEW-2026-10-19.zh-CN.md` 中的同步写盘问题，继续在 `lincoln-0.2.20` 修改本地源码，保留上轮三个性能改动。目标是消除主线程和音频诊断回调中的磁盘等待，并保留正常负载下的日志顺序、尾部、脱敏及历史格式。

## 实现及防退化约束

| 环节 | 行为与保护 |
| --- | --- |
| 初始化／轮转／写入 | 一个后台写入线程执行；调用方只创建不持有 Activity 的日志句柄并提交已脱敏、带原始调用时间的有界文本。普通日志、音频诊断和既有连接诊断共用此入口 |
| 打开新会话 | 同一路径的旧句柄停止接受新记录；此前已入队的条目仍按 FIFO 写完，然后新会话初始化、轮转。旧句柄后来的回调和关闭不能写进或关闭新会话 |
| 关闭 | 停止接受新条目，不取消已接受的尾部；可将最后一条和关闭合为同一个入队边界。不会在主线程等日志文件锁 |
| 初始化条目被挤出队列 | 初始化元数据保留在会话句柄中，第一个仍待写的条目会先初始化和写头部，不依赖一个可能被挤出的控制命令 |
| 文件格式 | 继续使用 `SessionLogFile` 的 `diplay.log` 和七份历史文件、512 KiB 轮转阈值；时间格式和已有脱敏规则保留。文件包装对象不持有常驻流，每次文件操作自行关闭流 |
| 导出 | 原有后台导出线程最多等待 1 秒，等待范围是开始等待前已入队的批次，不被后续持续日志无限延长。超时写入报告状态，未完成条目继续排队 |
| 主动退出 | 既有后台销毁流程在杀进程前最多等待日志批次 1 秒，不在主线程等待；慢存储不能使退出永久停住 |

队列最多容纳 1024 个待处理条目，另有一个正在处理的条目。文本在入队前脱敏并截断。所有会话复用写入线程，不为每个 Activity 新建线程，也没有不受容量限制的“初始化／关闭命令”旁路。

同一 Activity 内旧控制器的 `CONNECTION_DIAGNOSTIC` 仍可以写入它捕获的当前日志句柄；原有“保留销毁诊断但拒绝旧控制器普通状态”的逻辑未删除。

Host 的既有 `singleTask` 模式保留；普通返回前台不会新建日志会话，也不会额外轮转。

## 必须明确的限制

- 正常负载下按顺序保留已接受记录。若存储长时间不响应且待写条目超过 1024，丢弃最旧待写条目以维持内存上限；恢复后写入丢弃计数，导出也包含累计计数。不是无损、无限容量的队列。
- 导出等待超时会明确标为 `pendingCompleted=false`，不伪称已包含全部尾部；后续导出仍能包含稍后写完的记录。
- `pendingCompleted=true` 表示此前入队条目已处理或按容量策略被挤出，不代表每次磁盘写入都成功；累计丢弃数会同时显示，磁盘错误仍按既有尽力记录规则处理。
- 进程被系统立即强杀或车机断电时，仍可能存在尚未写出的异步日志；1 秒主动退出等待不能覆盖这些情况，也不是 `fsync` 耐断电承诺。已有独立崩溃记录机制未改动。
- 这次调整日志调度，不改变 CarPlay 连接状态机、PCM 数据、音频焦点或导航协议。回归验证不等于证明所有实车固件都绝无回退。

## 复现与对抗性检查

- 修改前，真实 `SessionLogFile` 文件锁被占用时，Host 日志调用及“入队后关闭”的 4 项检查全部失败，覆盖 Android API 27、33。
- 修改后，同样占用文件锁时调用方返回；解除阻塞后验证实际文件中的尾部内容，而不只检查函数返回。
- 覆盖慢初始化、已关闭句柄的排队尾部、新旧会话竞争、旧销毁回调、初始化条目被挤出、有界丢弃计数、连续十次会话的八文件历史、按大小轮转、脱敏和原始时间戳。
- 覆盖首次初始化失败重试、写入失败后继续记录、等待超时不取消记录、线程中断标志保留，以及等待批次被部分挤出时仍能正确结束。
- 覆盖后台导出实际文本中的新记录／超时状态，以及主动退出在尾部写出后才杀进程、存储持续受阻时仍有退出期限。
- 沿用主题诊断、VPN 授权、旧控制器销毁证据、平滑视频生命周期及报告导出等既有断言，只为异步语义在读取实际文件前等待。
- 独立撤除实验：在写入端错误地跳过已关闭句柄，会重现 2 项尾部／会话归档失败；去掉主动退出的后台等待，会在两个 Android API 重现“尾部尚未写入就杀进程”。实验后逐字节恢复两个源码文件，再执行完整检查。
