# 林肯仪表导航误报：修复方案与对抗性审查

状态：**已被重新审视的方案取代**。此前测试 APK 中“换路口等待新距离”和“仅状态 2 生成终点”的实验性行为可能导致提示缺失，已从工作区导航输出撤回；以 `v1.2.0` 作为当前行为基线。下文实施描述是当时的记录，不代表当前工作区。现行方案见 `LINCOLN-NAVIGATION-ROBUST-PROPOSAL.zh-CN.md`。

实施验证：默认林肯接收器不再把活动路线的终点类动作当成已到达；明确状态 2 后发送终点并在短暂显示后清理。新路口缺少可信距离时撤除旧提示并等待新距离；其他接收器保留原输出策略。诊断为限速、有限内存队列，导出时读取，发送成功仅说明系统接受调用。针对性测试覆盖结束、取消、快速新路线、广播失败、重规划和进度；这不等于实际仪表画面验证。

已在模拟器中调用提供的 InstrumentPanel 1.0 运行时转换函数，确认 `turn_dest` 与直行等映射不同；空路名在该接收端不会填入 `StreetName`，是否清除旧道路名取决于仪表固件，不能从该 DEX 保证。手机长期不提供能关联到新路口的距离时，仪表会暂时没有导航提示，这是保守处理的已知代价。

## 已确认事实与尚未确认的部分

1. 人工构造活动路线 + 非零距离 + 动作 10/12/24/25/27，基础广播立即发送 `turn_dest`；这与用户的误报现象相容，但不能证明当时真实数据相同。兼容开关开启时，附加通道也能发送对应终点动作。
2. Apple 的 `CPManeuverType` 有到达目的地及左右侧等类别；已有其他车机逆向实现把上述类型归入到达类。不能仅因这几个值相同地映射为终点就宣称该编号定义错误；要区分手机描述的“目标动作”和仪表展示的“已经到达”。
3. 提供的 InstrumentPanel 1.0 DEX 表明该接收端将 `turn_dest` 映射成固定仪表路段代码，转换函数不接收路线状态或距离。车机最终是否必然显示“您已到达”，仍需匹配实际固件和接收器验证。
4. 新路口索引到达但本路口新距离未到时，已经构造出将前一路口的距离用于新标识及进度基准。距离先到、索引后到也是可能的输入顺序，但无索引的距离帧不能仅凭到达时间确定归属。
5. 当前 `routeEnded` 合并了到达和其他结束原因；状态 2 到达会清除当前路线，并不会自动合成一条终点指令。单纯把现有终点动作推迟到状态 2 会导致正常终点提示缺失。
6. `0x0d` 两个索引的含义存在不同设备和数据分析解释；当前 DiPlay 用第一个。构造测试证明选择方式，未证明应固定改为第二个。

参考：[Apple CPManeuverType](https://developer.apple.com/documentation/carplay/cpmaneuvertype)、[另一实现对动作编号和列表首项的逆向记录](https://github.com/KidMixer/mazda-carplay-hud/blob/main/mazda/patches/blmjcicarplay/nav.cpp)、[另一份实测对双索引列表的解释](https://github.com/lvalen91/CPC200-CCPA_resources/blob/main/documentation/02_Protocol_Reference/iap2_message_catalog.md)。这些是不同设备/来源的证据，不能代替用户高德实车数据。

## 批次 1：本地补充可定位的诊断，不要求先去实车采集

- 只在导航状态、活动索引/列表、动作类型、距离修订、输出类型、路线代次或异常决策变化时记录。内容限于进程内尝试编号、单调相对时间、数值状态、列表长度及有限索引、距离是否存在及数值/修订、兼容开关和发送/清除结果；不记录经纬度、路名、地址、歌曲、原始载荷或设备标识。
- 最近事件采用 128 条有界队列，标记丢弃数；普通距离变化最多每秒记录一次，动作/状态/异常决策变化优先记录并对相同事件去重，突发变化采用每秒有界配额并累计省略数及最新状态。事件入队后异步写盘或导出时读取内存，不能同步等待磁盘、网络或阻塞导航。导出时包含误报前后的短窗口；旧有连接耗时日志不当作仪表日志。
- 输出决策记录区分基础广播、辅助广播、HUD socket 和广播 API 成功/失败；API 成功只表示已提交，不表示仪表消费或渲染成功。
- 验证导出路径、脱敏、上限、丢弃、后台线程与阻塞磁盘、空/重复帧、并发事件和关闭/重连；主线程与车辆安全关键路径不做同步 I/O。

**执行顺序：** 用户表示专门实车测试较麻烦，因此不以事先采集实车日志作为本地实现、测试的前置条件；诊断可随修复一起进入同一个测试包。先利用现有源码、提供的仪表 APK 和合成导航帧验证可确定的问题，不以假设改变索引协议。若后续正常使用中再次出现误报，再按需记录源动作、原始列表长度/索引、距离有无、路线状态和同一时刻 CarPlay 下一动作，并注明地图、兼容开关与仪表接收器版本。

## 批次 2：建立无歧义的状态与距离来源

保持原有 iAP2 解析、其他品牌输出及已验证的 0x0d 选择行为；向 Lincoln 消费路径补充必要元数据，而非让其他输出跟随新策略：

1. 保留路线代次、动作索引、距离是否实际出现、距离修订及事件顺序；区分缺失和真实 0。不得把初始化默认 0 当作手机发出的 0，也不得用总剩余距离替代下一动作距离。
2. 同帧包含当前索引和距离时，可作为该次状态的候选；当前索引明确建立后收到的新距离可在无已知冲突的情况下作为候选。索引变化前的无索引距离单独留作不确定候选，**不因相差几百毫秒就认定属于新路口**。同帧语义仍受实际手机协议影响，数据异常时不能声称绝对可信。
3. 收到新索引但尚无可关联距离，不用旧索引的距离建立新进度身份。已经明确进入新动作且不能安全显示时，撤掉本输出的旧导航提示，等待新的有效数据；不合成直行/终点或假 0 m。若手机一直只发一次无索引距离且无新样本，仪表可能保持空白；这是真实可用性取舍，须在实车统计并在发布验收中接受或重新设计，不能宣称必然兼容所有地图。
4. 普通同一路口距离递减即时输出，真实 0 只有在手机实际发送且归属明确时作为距离处理，并不单独证明到达。总剩余距离可能是旧值、缺失、途经点或与路口距离不同，不能设置一个固定米数阈值认定到达。
5. 明确新路口/新路线/重新规划后，**只有在可信距离确定时**建立新的 token 与起始距离。相同路口继续沿用既有防抖、距离精度和每秒保活；空列表短暂缺帧不建立新基准、不重置进度。无新样本、旧快照、歌词及保活均不算新距离。
6. 0/1/2 个以上列表项、先距离后索引、先索引后距离、同帧、间隔较久、缺帧、手机复用索引和迟到快照都必须覆盖。未能明确关联的数据保留可追溯状态并最终放弃，不强制用过期值填充。

## 批次 3：终点、取消和重规划的输出策略

- 增加与路线代次绑定的结束原因：`ARRIVED`（手机状态 2）、`NO_ROUTE`（状态 0）、`DISCONNECTED` 和 `UNKNOWN`。在解析器清除当前详情前记录原因；不能将 0 当作 2，也不能把缺失距离、假 0、仅终点动作或过期剩余距离当作已到达。
- 路线仍活动时，接近终点的动作与已到达状态分开处理。**如果尚无经过目标仪表确认的“接近终点但不显示已到达”的代码，不发送可能误报“已到达”的 `turn_dest`，也不虚构转弯。** 已确认真正到达状态 2 时，再使用经接收端验证的终点提示，保留短暂可见时间后发送本应用持有状态的 `STATE_OFF`；正常取消、断开不显示“已到达”。新的提示序列是否需要先发送 `STATE_ON`、空道路名如何显示，必须先按真实接收端和目标仪表验证，不能自行假定。
- 这意味着在终点前，如果原车仪表不支持准确的“即将到达”展示，可能暂时没有终点图标；手机画面不受影响。不能同时承诺既完整保留所有提前终点图标又绝不显示“已到达”，需要实际仪表验证可用的中性表示。
- 终点提示必须按代次只发一次，按实际所有权清理。若到达后很快开始新路线，旧延迟清理不能关闭新路线。普通空帧仍保留最近可信指令和原 token；明确换路口、重规划、真正结束和连接切换则按对应边界处理。
- 代次只能隔离本机已知的前后状态与迟到回调，不是手机发来的全局路线 ID；如果手机本身发送无法识别为旧路线的迟到状态，不能声称代次机制可以百分百识别。
- 扩展辅助广播和 HUD socket 必须与基础输出使用同一决定，不得一个显示终点另一个显示转向。清理只针对本应用持有的状态；增强通道包括全局广播，不能假设其他原车地图一定不受影响，需验证及记录；兼容模式关闭时不得增加该通道。
- 优先用已提供的 InstrumentPanel 1.0 运行时 DEX、可执行的接收器方法或基于反汇编的独立模型，验证状态、图标、距离与清除顺序。构造数据/接收器模型可以证明包字段，不能代替实际接收与车机画面；不把空字符串、-1 或未知 icon 猜作已支持的中性显示。目标车机是否按预期显示可在用户下次正常使用时顺手核实，不要求现在专程测试。

## 对抗性审查与验收

| 场景 | 验收条件 |
| --- | --- |
| 活动中、非零距离和上游终点类动作 | 不编造已到达或其他方向；无已验证中性编码时可暂时空白，并在诊断注明原因 |
| 真正状态 2、取消状态 0、断开 | 2 的终点提示与延迟清理按验证后的协议运行；0/断开不误报到达；旧定时任务不得影响新路线 |
| 相同帧、索引先到、距离先到、缺失、0 与异常距离 | 不把缺失冒充 0，不把前一路口的旧距离用作新基准；对无法判定归属的数据按上述策略保守处理 |
| 正常转向/环岛/掉头/上下匝道/未知值 | 已支持的动作映射与正确距离保持；不借此改其他厂商映射；未知值不新增伪造方向 |
| 距离抖动及重规划 | 沿用 1–4 m 抖动、5–49 m 多帧/5 s、≥50 m 两帧/1 s 保护；真实换路口和规划后重建基准，无空帧/歌词误重置 |
| 静止/空列表/瞬时 NoRouteSet | 短暂断帧保持可信卡片并按现有频率保活；真正退出仍按现有防闪烁窗口关闭 |
| 兼容开/关、接收器重启、广播失败 | 两套通道互不矛盾；无误改其他应用的成功宣称；丢包/重启/异常发送后能安全恢复，保持有效 token |
| 回调并发、旧事件、快速新路线/会话 | 保持输出锁内最新快照策略；旧终点、旧清理、旧进度不覆盖新路线 |
| 其他功能 | 歌词和音乐播放独立不改；有线/无线、后台启动、设置/备份和其他厂商输出不改变 |
| 真机 | 验证高德：连续普通路口、目的地前有路口、途中重新规划、抵达/取消、拔插重连；比对手机提示、仪表箭头/距离/进度与诊断记录。车机与安装的仪表 APK 版本要明确 |

执行时先把七项“观察现状”的构造测试改写为修复后的正确行为断言，避免把已知错误固化为正确契约；结合现有 `LincolnClusterOutputTest`、`LincolnManeuverTrackerTest`、`LincolnClusterProtocolTest`、`BydHudRouteStateTest`、诊断/并发测试定向回归。若改动触及共享解析行为，增加相应模块测试；按 AGENTS.md 做受影响主应用构建，不因非 UI 修改运行截图矩阵。

自动化与接收器证据通过后，可交付本地测试包并说明验证范围；用户下次正常使用时顺手核实即可，不要求专程跑实车或必须提供日志。只有目标车机实际核实后，才能声称用户实车问题已经解决。无一组测试能证明所有地图/iOS/车机组合绝无回退。
