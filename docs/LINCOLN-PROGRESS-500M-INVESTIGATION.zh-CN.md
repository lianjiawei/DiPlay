# 仪表进度在远距离刷新：源码与本地回放

用户反馈约 500 米以上偶尔重刷。本记录描述源码分析和合成回放，不代表已经取得该次实车的手机帧或仪表日志。后续工作区中的生产逻辑调整见《LINCOLN-PROGRESS-STABILITY-PROPOSAL.zh-CN.md》。

用户进一步说明：观感更像进度条短暂消失，然后快速从满的位置过渡回合适位置，不一定是数据真的重置为 256。之前的“刷满”仅指回放中数值基准重置，不能等同于用户观察到的实际视觉过程。

用户随后确认：异常发生时箭头和距离仍在，且“仪表兼容”开关关闭。因此 DiPlay 自身的附加 HUD Socket 路径不应作为本次默认原因；其他应用或仪表自身的路径是否活跃尚未知。

进一步核实 `v1.2.0` 及当前代码发现一个可复现的冗余发送：主 `INFO` 消息的判重 key 包含整段路线的剩余距离和时间，但它实际发送的 INFO 只有动作、到下一路口的距离、路名和合成身份；剩余距离及时间另经 `REMAIN` 发送。即使 `REMAIN` 开关关闭，只要剩余距离或时间变化，也会让未变化的主 INFO 再发一次，不受一秒保活间隔限制。合成回放以 100 ms 间隔只改变剩余距离，在 300 ms 内发出 4 次相同主导航内容；这是构造输入，不代表实车实际更新频率。本地回放校验同一动作、距离、身份和按 APK 公式计算的进度值不变，无法验证真实固件是否因此重新绘制。

这是明确可减少的重复发送，但尚无证据证明它导致进度条的短暂消失。当前工作区已去掉默认仪表因无关剩余字段导致的额外 INFO，保留一秒保活、实际路口变更、进度标识变更、恢复与 REMAIN 独立通道；自定义接收器保留原策略。不能单纯停发 INFO 或禁用保活。

DiPlay 为维持导航卡片会定期重发 `INFO`；每次收到 INFO，提供的仪表 APK 将导航 Bundle 交给 `AsyncTask`，由它调用车机服务的 `sendEvent`。这证明数据会重复提交，不证明最终仪表固件会每次重建进度条或播放动画。数据发送间断、仪表导航状态清除/重启、其他导航来源竞争以及固件渲染，都可能表现为消失与重现，但没有接收端与画面同步证据时不能确定。不要仅凭该现象调低保活频率，因为已有防闪烁逻辑依赖保活。

## 接收器与约 483 米字段

补充对提供的原车百度地图 APK 的检查：`PacketJSONData.packetManeuver`（`classes3.dump` code item `0x32a510`）从导航 Bundle 的 `remain_dist` 获取距离，经 `formatDistance` 输出；若该键不存在，直接把 HUD 消息的 `distance` 填为 0。`formatDistance`（`0x329f30`）将负数置 0，并按距离分段取整，在所检查的打包方法中未见基于上一次距离的突降确认。该方法还会在当前道路名为空时不发送这一条消息。提供的仪表 APK `NavPresenterImpl.sendNaviInfo` 中未发现远距离骤降为 0 的确认逻辑，直接使用收到值计算；这不证明百度原始导航引擎或车机固件其他部分没有保护，也不证明用户手机发送了异常值。

用户提供的 InstrumentPanel 1.0 运行时 DEX 的 `NavPresenterImpl.sendNaviInfo`（code item `0x223850`）中，广播 `distance` 同时传给第一个与最后一个整数参数。前者与 482.802 比较，整数距离不低于 483 时 `PropertyOfDistance=1`，不高于 482 时为 0；该值与距离显示字段及 `BargraphSteps` 一起发送给车机服务。原车 HUD 的调用中，这两个整数分别来自 `getManeuverDistance()` 与 `getDistance()`，不能假定总是相同。

该分界**不是**进度计算中重新记录起始距离的条件。`BargraphSteps` 使用最后一个整数作为当前距离，坐标字段变化时以它作为新基准，基准不为 0 时计算 `当前距离 / 基准距离 × 256`。接收器方法中没有按 500 米周期取模或循环刷新的分支；但因 `PropertyOfDistance` 被交给车机固件，且固件的最终绘制未知，不能排除字段切换对显示形式产生影响。只跨过一次 482/483 米也不能解释一直在 500 米以上反复重刷。

## 已复现的发送端边界

针对 `v1.2.0` 的合成 `0x5201/0x5202` 回放走实际解析、快照、基础广播，并用 APK 的公式模拟进度；兼容开关开、关都验证。相同动作编号的手机原始距离为：

`900 → 800 → 820 → 818 → 816 → 814 → 812 → 810 → 790` 米，更新间隔约 1 秒。

旧规则会先把回升期间的输出保持在 800 米；后续尽管 820 到 810 连续下降，但它们始终比本路口最低的 800 米高至少 5 米，且满足至少 3 个新帧、5 秒确认时间，所以 810 米触发 `persistent-distance-increase`，更换合成坐标，接收模型的进度重置为 256。当前工作区在 5～49 米回升且最后新帧仍下降时最多再等待 2 秒；`fallingCorrectionResumesWithoutResettingTheProgressIdentity` 回放中 790 米恢复到旧基准以下，不再重算。该改动不证明手机当时一定发送了这些数据。

`crossingFiveHundredMetersAloneDoesNotResetTheProgressIdentity` 回放 900 → 800 → 600 → 501 → 500 → 499 → 483 → 482 → 400 米，在动作编号和路线代次不变时始终使用同一个发送端标识。该接收模型只模拟进度公式，不能代替仪表固件的 `PropertyOfDistance` 渲染。

## 其他会建立新基准的路径

- 当前动作编号或本地路线代次变化，例如手机上报 Loading/Rerouting；真换路口和真实重规划需要重新起算，但输入不稳定也可能导致视觉刷新。
- 连续回升达到门槛、初始零距离恢复、会话重连、仪表相关输出重建、发送异常后的恢复。状态判定与容错在 `LincolnClusterProtocol.kt`、`LincolnClusterOutput.kt`。
- 若仪表 APK 进程自身重启、其他来源向同一接收器发送不同坐标、接收顺序变化，或目标车机固件另有逻辑，也可能改变基准或画面；发送成功不代表接收成功。

## 可观察性与后续边界

现有发送端日志的 `nav progress baseline reason`、索引、路线代次、原始/发送距离和新增有界帧诊断能区分大部分发送端新基准；它们不能证明仪表最终收到和如何绘制。若后续自然使用时保留一次异常前后的报告，结合观察到的距离和兼容开关，可进一步区分；不要求为此次分析专门开车。

下一步若优化回升确认，要同时验证真实倒车、绕路和重规划，不能单纯加大阈值或永久锁定身份，否则可能把真实距离冻结、令无钳制接收器的计算溢出、或丢失新路口进度。当前只有合成数据和发送模型，无法确定这套回升规则就是用户车上现象的唯一原因。
