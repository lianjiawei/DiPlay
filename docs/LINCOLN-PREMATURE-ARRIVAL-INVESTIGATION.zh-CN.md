# 林肯仪表提前显示到达：源码构造调查

状态：以下为修复前基于 `v1.2.0` 的调查记录；后续对“明确换编号但新详情缺失时重发旧终点”做了窄范围修复，见 `LINCOLN-NAVIGATION-ROBUST-PROPOSAL.zh-CN.md`。实车发生时的手机原始导航数据尚未采集。

## 构造方法及范围

`LincolnPrematureDestinationInvestigationTest` 使用合成的 iAP2 `0x5201`/`0x5202`，经过实际的 `BydHudRouteState → CarPlayGlance → LincolnClusterOutput`，检查发给仪表的 Android Intent。兼容模式使用替身 HUD socket，不启动真实端口。七项定向测试通过；其中第一项组合了五种动作编号和两种兼容开关状态。

这些测试证明**指定输入必然产生指定广播**。没有运行真实 iPhone，也没有让原车仪表最终显示画面，不能据此断言实车当时发送了这些数据或认定此次误报的唯一原因。

## 复现结果

1. 手机提供路线活动状态 `1`、当前动作编号 7、动作类型 24、距动作 400 m、路线剩余 5000 m。广播为 `name=turn_dest, distance=400`，没有等待到达状态 `2`，也没有检查总剩余距离。类型 10、12、24、25、27 均如此；“仪表兼容”开或关，基础广播均如此。开启时辅助广播与 HUD socket 也发送终点类型 24。这里仅证明状态未结束、发送了终点类型；动作 24 在不同手机地图上的具体语义需以其数据为准。
2. 先收到路口 7 左转、距离 400 m；新路口 8 的类型和索引到达，但新距离帧未到。输出立即变成路口 8 的 `turn_dest`，距离仍为路口 7 的 400 m；且新标识建立在这 400 m 上。随后新距离 150 m 到达时标识未重置。按照已分析仪表接收端的公式，基准为 400 时进度是 `150/400*256=96`，而不是以 150 m 作为初始基准。此测试不推断实车该次数据的实际先后。
3. 新路线尚未收到任何路口距离帧时，解析器的距离默认值为 0；若动作已被识别为终点，输出也可为 `turn_dest, distance=0`。缺失与真实 0 在当前快照中不能直接区分，不能仅凭 0 判断实际到达。
4. `0x0d` 有两个索引 `[7, 8]` 时，当前解析器选择第一个 7；即使 7 是终点、8 是右转，也输出终点。只证明代码选择方式，**不证明**实际手机列表第一个是旧项或第二个才是下一路口；具体语义须核对真实帧。
5. 若上次已发送终点、后续收到新路口的详情但当前列表暂时为空，现有防闪烁保持与每秒重发机制会继续发送上次终点。当列表明确选中新路口且距离到达后，恢复正确转向。不能把每次空列表都当作路线结束，否则会引起路口指示闪烁。
6. 另一种分帧顺序中，先收到 150 m、后收到新路口索引，后者未再携带距离，当前代码会让新路口使用已缓存的 150 m。该距离帧不含路口索引，**不能仅从这个构造确定它实际属于哪个路口**；但这证明无条件丢弃索引变化之前到达的所有距离会改变当前行为。
7. 如果当前是右转提示，接着收到真正的 `Arrived` 状态 `2`，解析器清除导航，输出在结束稳定窗口后发送 `STATE_OFF`，并不会凭这个状态另外合成一条 `turn_dest`。因此不能简单地把所有终点动作都延迟到状态 2 才发，否则正常终点提示可能丢失。

## 已提供仪表 APK 的接收端核对

使用先前从用户提供的 `InstrumentPanel_Optional 1.0` 提取的运行时 DEX，SHA-256 为 `4a322cde82fa501e066c5f20418b0d5833c59dade6e8d92b9d14c7b73b3b390e`。广播处理方法 `0x23aea0` 读取 `name` 和 `distance`，把 `name` 交给 `InduceSwitchUtil.switchInfo(name)`。该方法在 DEX code item `0x2272fc` 中，`0x22759e` 的 `turn_dest` 分支固定返回 1 个路段及 `{DirectionAndNumber:0xC0;ManeuverElement:0x13}`；该映射不接收距离或路线状态。

`NavPresenterImpl.sendNaviInfo` code item `0x223850` 再把路段字符串与距离、进度封装给车机仪表服务。可以确认 `turn_dest` 被转换成固定的仪表路段描述，**不能仅据此确认车机固件如何绘制“您已到达”或用户车辆一定使用完全相同的接收端版本**。原始 APK 的进度计算和坐标字段证据见 `LINCOLN-CLUSTER-PROGRESS.md`。

## 后续修复的边界

- 应区分路线仍在进行、接近终点、真正到达及方向不明，不把“未知”伪装为直行；保留终点提示在真正到达时的可用性。
- 路口标识和距离允许分帧且顺序可反转。不能无条件要求距离只能在索引之后到达，否则可能丢掉已先收到的有效数据；应防止将前一动作的距离误当作新动作的基准，并明确无新距离时的显示策略。
- 不能直接删除空帧保持机制，否则会恢复已修复的导航闪烁。兼容开关开、关和已验证的进度条、真实导航结束、路线重新规划均需覆盖。
- 手机多条索引的真实含义未确认；不要仅凭构造数据改变索引选择顺序。实际路口动作、剩余距离、路线状态、距离帧修订和输出类型需在复现时采集；现有有线连接耗时日志不覆盖这条仪表诊断链路。
